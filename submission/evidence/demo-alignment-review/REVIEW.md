# 데모 영상과 강조 표시 정렬 검토

검토일: 2026-09-09. 대상은 현재 공개된 `product-demo-v4.mp4`입니다. 새 데모를 만들거나 렌더러·웹페이지·공개 파일을 변경하지 않았습니다. 기존 영상을 읽어 증거 프레임을 추출하고, 필터의 출력 프레임 수를 null 출력으로 진단했습니다.

## 결론

현재 문제는 단순히 테두리 좌표를 조금 옮기는 것으로 해결되지 않습니다. **앞에 넣으려던 정지가 적용되지 않는 시간 처리 오류**와 **스크롤 전 좌표를 스크롤 후 장면에 사용하는 공간 오류**가 동시에 있습니다. 여기에 설명이 요구하는 행동과 강조 대상이 다른 장면이 섞여 있습니다.

현재 서버 파일과 로컬 v4의 SHA-256이 같습니다. 서버에서도 문제가 있는 동일 파일이 제공되고 있습니다. 앱 화면과 강조가 같은 MP4 안에 합성되어 있으므로, 웹페이지에서 영상 크기를 줄이는 것만으로 둘 사이의 상대 위치가 달라지지는 않습니다. 브라우저 캐시나 웹페이지 배율을 우선 원인으로 볼 근거가 없습니다.

기존 검증은 영상 재생·해상도·이동 재생·페이지 오류·모바일 넘침을 확인했습니다. **강조의 위치, 켜고 끄는 시점, 정지 구간의 실제 적용, 설명과 클릭 대상의 일치는 검사하지 않았습니다.** 이전 검증을 근거로 정렬 문제가 해결됐다고 판단한 것은 충분하지 않았습니다.

## 1. 시간 처리 오류: 정지는 앞이 아니라 뒤에서 생깁니다

현재 순서는 `trim → setpts → tpad(앞에 정지 추가) → fps=30 → drawbox → crop/scale → 반복되는 설명 PNG와 overlay`입니다.

이 원본 WebM을 `tpad`에 넣기 직전 필터 링크의 프레임률은 `1/0`으로 나타납니다. 이 상태에서는 `start_duration`으로 요청한 정지 분량이 추가되지 않습니다. 화면 설명 PNG는 계속 반복되므로 합성은 `-t`로 지정한 길이까지 이어지고, 원본 화면이 끝난 뒤 마지막 화면이 반복됩니다.

따라서 사용자가 보는 동작은 처음부터 진행되는데, 강조 종료 시간은 정지가 들어갔다는 가정으로 계산됩니다. 마지막 프레임에 테두리가 남은 경우 그 테두리도 반복됩니다. 이는 렌더러의 `highlightPolicy` 설명과 실제 출력이 다른 이유입니다.

기존 필터를 그대로 null 출력으로 실행한 진단 결과입니다. 새 영상을 렌더링한 결과가 아닙니다.

| 장면 | 요청한 앞 정지 | 기대 길이 | 현재 영상 필터의 실제 길이 | 진단용으로 fps를 먼저 확정한 경우 |
|---|---:|---:|---:|---:|
| 샘플 시작 | 2.40초 | 3.05초 | **0.63초** | 3.03초 |
| 자료 선택 | 1.40초 | 7.40초 | **6.00초** | 7.40초 |
| 파일명 입력 | 2.60초 | 4.95초 | **2.37초** | 4.97초 |
| 저장 승인 | 1.00초 | 8.30초 | **7.27초** | 8.27초 |

작은 차이는 30fps의 프레임 경계 때문입니다. 중요한 차이는 요청한 정지 시간이 통째로 빠졌다는 점입니다. `fps` 위치를 바꾼 진단은 이 원인을 분리하기 위한 것이며, 제작 코드에 적용하지 않았습니다.

최종 영상의 보라색 테두리를 0.1초 간격으로 측정했을 때, 첫 장면은 거의 전체 구간에 남고 파일명 입력 장면은 약 23.5~28.0초에 걸쳐 남습니다. 파일명 장면의 의도한 종료는 약 25.73초입니다. 범위는 색상 검출 근사치이며 전환 구간은 포함될 수 있습니다. 정확한 증거는 `highlight-timing.json`, `padding-probe.json` 및 `padding-*.log`입니다.

## 2. 공간 오류: 약 19초 장면의 자료 목록

현재 출력 약 **19.25초**, 원본 약 **24.4초**의 ‘자료와 결과를 함께 확인해요’ 장면에서 명확히 재현됩니다.

- 원본 20초에는 첫 자료 카드의 상단이 약 y=306입니다.
- 원본 24.4초에는 첫 카드 상단이 약 y=190입니다. 화면이 약 **116px 위로 이동**했습니다.
- 그러나 이 장면의 강조 상단은 기존 값인 **y=275**입니다. 높이 402이므로 아래쪽은 y=677입니다.
- 결과적으로 첫 자료 카드의 위쪽과 이름을 놓치고, 아래의 안내 문구와 ‘자료 다시 찾기’ 제목까지 포함합니다.
- 최종 출력 배율에서 116px은 약 **128px**입니다. 1~2px 반올림 문제가 아닙니다.

같은 범위를 계속 안내하려면 y=159 부근이 측정 후보입니다. 다만 이 값을 그대로 수정안으로 확정하면 다시 수동 보정이 됩니다. 사용할 정확한 정지 프레임과 ‘자료 제목 포함/카드만 포함’ 범위를 먼저 정한 뒤 다시 측정해야 합니다.

증거: `raw-2.png`, `raw-3.png`, `final-3.png`. 전체 비교는 `scene-comparison.jpg`입니다.

## 4. 왜 이전 수정으로 충분하지 않았는가

1. 강조를 crop/scale 이전 원본 좌표에 그리는 접근 자체는 타당합니다. 앱과 테두리가 같은 변환을 받으므로 배율 오차를 줄입니다. 하지만 **잘못된 원본 좌표를 정확하게 확대할 뿐**이며, 스크롤 상태가 다른 문제를 해결하지 않습니다.
2. `hold-.12`라는 종료 시간만 계산하면 실제 정지가 있다는 가정이 숨어 있습니다. 실제 프레임 수를 확인하지 않아 그 가정이 깨졌습니다.
3. 모든 장면에서 사각형 하나가 ‘읽을 영역’과 ‘클릭할 버튼’ 역할을 동시에 맡습니다. 위치가 맞아도 설명과 일치하지 않는 느낌이 남습니다.
4. 앱 화면 쪽 번호·태그를 만든 `coach-*.png`가 존재하지만, 현재 최종 필터는 `panel-*.png`만 합성합니다. 세 번째 입력인 coach PNG는 연결되지 않습니다. 따라서 최종 영상은 큰 테두리와 왼쪽 단계 번호만 보이며, 설명과 대상의 연결이 약합니다.
5. `guide_until` 같은 이전 설정과 쓰지 않는 레이아웃 코드가 남아 있습니다. 설정 하나가 실제 출력에 어떤 영향을 주는지 불명확합니다.
6. 완성 화면 전체를 0.3초씩 겹치는 전환은 서로 다른 앱 상태·설명·강조까지 겹칩니다. 전환은 좌표 오류의 직접 원인은 아니지만, 경계를 더 모호하게 만듭니다.

## 5. 권장 제작 구조 — 아직 구현하지 않은 검토안

### 화면 상태와 대상부터 고정

각 장면에 사용할 정확한 원본 프레임, 대상의 이름, 경계, 원본 해상도, 스크롤 상태를 함께 기록합니다. ‘대략 자료 패널’ 대신 ‘선택된 자료 세 개’, ‘저장 경로 입력란’, ‘이번만 허용 버튼’처럼 대상을 명시합니다. 기존 녹화 도구가 이미 앱 요소를 찾아 클릭하므로, 재녹화가 필요할 때는 같은 요소의 화면 좌표도 동시에 기록할 수 있습니다.

기존 영상으로 해결 가능한 부분은 정확한 프레임에서 다시 측정합니다. 메뉴 클릭이나 화면 전환이 원본에 충분히 남아 있지 않은 장면만 재녹화 대상으로 판단합니다. 전체 재촬영부터 시작할 필요는 없습니다.

### 정지 안내와 실제 동작을 별도 구간으로 구성

한 장면을 `대상 확인 → 정지 안내 → 강조 해제 → 실제 조작 → 결과 확인`으로 나눕니다. 정지 안내는 지정한 프레임 한 장을 명시적으로 유지합니다. 실제 조작 구간에는 강조를 넣지 않는 것을 기본으로 하고, 움직이는 대상을 추적해야 하는 구성은 이번 간단한 데모에 도입하지 않는 편이 낫습니다.

이렇게 하면 ‘정지했다고 가정한 시간’과 ‘실제로 정지한 프레임’이 달라질 여지를 줄입니다. 앞에 fps를 확정하는 최소 수정은 필요하지만, 반복되는 PNG 입력이 부족한 영상 길이를 조용히 늘리는 구조까지 남기는 것은 권장하지 않습니다.

### 프레임 단위로 시간을 관리

30fps를 먼저 확정하고 장면 길이·정지 길이·전환 길이를 정수 프레임으로 관리합니다. 장면 시작과 끝을 추정 초 단위로 계속 더하지 않고, 최종 출력의 프레임 수와 대조합니다. 설명 종료와 실제 클릭 시작은 최소 3~4프레임 이상 분리하는 것을 초안 기준으로 삼습니다.

### 한 화면에는 한 목적의 강조

- 위치 안내: 대상 영역 + 짧은 명사 설명.
- 행동 안내: 실제 버튼이나 입력란 + 행동 문장.
- 결과 안내: 바뀐 상태나 결과 한 곳 + 완료 문장.

라벨은 대상의 글자를 가리지 않는 빈 공간에 놓고 필요하면 짧은 연결선을 사용합니다. 전체 페이지를 감싸는 큰 테두리를 ‘클릭 안내’로 사용하지 않습니다.

### 읽기 시간과 전환 조정

현재 계획대로 앞 정지가 적용되더라도, 자료 재확인 장면의 충분히 보이는 강조 시간은 전환 0.3초와 해제 여유 0.12초를 빼면 약 0.68초, 승인 장면은 약 0.58초입니다. 처음 보는 사람이 설명을 읽고 대상을 찾기에는 짧습니다. 일반 안내 2.5~3.5초, 승인 검토 3~4초 정도를 초기 편집 기준으로 검토하되, 실제 문구 분량과 시청 테스트로 정해야 합니다. 총 길이 47초를 먼저 고정하고 읽기 시간을 줄이지 않는 편이 좋습니다.

앱 상태가 바뀔 때는 앱 화면을 명확하게 전환하고 설명 패널만 짧게 전환하거나, 강조가 없는 구간에서만 화면 전환을 사용합니다. 두 상태의 강조가 동시에 보이면 실패로 봅니다.

## 6. 모바일 가독성은 별도 문제입니다

공개 페이지의 실제 영상 폭은 데스크톱 1440px 뷰포트에서 1198px, 모바일 390px에서 352px입니다. 영상 안의 29px 설명 문자는 각각 약 18.1px, **5.3px**로 보입니다. 모바일에 가로 넘침이 없다는 검사만으로 읽기 쉽다고 판단할 수 없습니다.

모바일 대응은 다음 중 하나를 선택해야 합니다. 별도 세로/확대 데모를 제공하거나, 인라인 영상의 글을 짧고 크게 줄이고 자세한 설명은 영상 밖에 배치해야 합니다. 단순 전체화면 버튼만으로 처음 보는 사람에게 친절한 인라인 데모가 되는 것은 아닙니다. 이 문제는 정렬 오류와 구분해 처리해야 합니다.

## 7. 새 제작에 들어가기 전 통과해야 할 기준

1. **정지 프레임 검증**: 지정한 안내 구간에서 앱 화면 픽셀이 실제로 정지해 있어야 합니다. 단순 길이 검사로 대체하지 않습니다.
2. **위치 검증**: 각 대상의 정확한 경계와 강조 경계를 같은 좌표계로 비교합니다. 초안 기준은 대상 바깥 여백 6~10px, 의도 경계와 차이 2px 이내로 두고 1080p 기준으로 확인합니다. 영역 안내와 버튼 안내의 허용 범위를 구분합니다.
3. **시간 검증**: 강조 시작 직전·직후, 클릭 직전, 강조 종료 직후, 스크롤 전후를 모두 추출합니다. 강조가 꺼져야 하는 프레임에 보라색 테두리가 남으면 실패입니다.
4. **설명 일치 검증**: ‘눌러요’라는 문장의 대상이 화면에 보여야 하고, 강조도 해당 대상이어야 합니다. 메뉴가 crop 밖에 있으면 실패입니다.
5. **전환 검증**: 서로 다른 앱 상태 위에 두 강조가 겹치지 않아야 합니다.
6. **가독성 검증**: 1080p 원본과 실제 페이지 크기에서 각각 확인합니다. 모바일 글자 크기와 읽기 가능성은 별도 판정합니다.
7. **회귀 검증**: 첫 장면뿐 아니라 모든 장면을 검사합니다. 잘 맞는 파일명 입력란도 유지되는지 확인합니다.

권장 다음 산출물은 완성 영상이 아니라 **7개 장면의 정지 프레임·대상 경계·설명 문구·표시 시간 표**입니다. 이 설계가 일치하는지 확인한 뒤, 가장 문제가 컸던 자료 재확인 장면과 파일명 입력 장면만 짧게 검증하고 전체 제작으로 넘어가는 순서가 적절합니다.
